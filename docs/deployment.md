# Deployment

This project ships two entirely separate release targets (roadmap `.vibe/decisions/022`, this repo's `.vibe/decisions/011`): a web build, and a native desktop/Android build. Only the web target is implemented and automated as of backlog item 008.

## Web: GitHub Pages

`.github/workflows/deploy-pages.yml` runs on every push to `main` (and can be triggered manually via `workflow_dispatch`):

1. Checks out the repo and installs dependencies inside a pinned `mcr.microsoft.com/playwright` container image (the same image `ci.yml`'s visual regression job uses, so a screenshot baseline captured through one always matches what the other renders).
2. Downloads the pinned `character` and `stage` WASM release assets into `public/wasm/` (drawing data, until backlog item 067 moves it to the core; see `docs/architecture.md`; `sff` is not a separate module here).
   It also builds the game core (`native/cmd/core-wasm`) with Go (`actions/setup-go`, version from `native/go.mod`) through `npm run wasm:core`, producing `public/wasm/core.wasm` and its `core-wasm_exec.js`, so the web build plays matches with the same library versions, and the same code, as the native one. Locally the same script runs inside the native toolchain container when no Go is installed. The web loads it to run every match (`src/wasm/core-bridge.ts`); the `engine` WASM is no longer downloaded or loaded.
3. Runs the full test suite (`npm test`), lint (`biome check`), the production build (`npm run build`), and the visual regression suite (`npm run test:visual`) — any failure stops the pipeline before anything is published.
4. Uploads `dist/` as a Pages artifact and deploys it.

The live app is reachable at `https://openkakutou.github.io/game/` once this pipeline has run successfully at least once against `main`. `dist/` is a fully static bundle — `vite.config.ts`'s `base: "./"` and every WASM bridge's default fetch URL (`./wasm/...`) are relative, so the build works unmodified whether served from a domain root or a GitHub Pages project subpath.

A missing or version-mismatched WASM asset at runtime (the pipeline's own download step used the wrong tag, or a CDN/cache served a stale file) no longer produces a blank page: the affected screen shows a clear, visible error message instead (see `docs/architecture.md`'s "never throw" bridge note).

## Native: Windows / Mac / Linux

A second, independent Go program in `native/` (`go-gl` + `veandco/go-sdl2`, no WASM, no webview) importing `character`/`stage`/`sff`/`engine` as native Go packages. Android is out of scope (roadmap decision `027`).

Everything native is built and tested inside a Docker image (`native/Dockerfile`: Go, SDL2 and SDL2_mixer headers, `pkg-config`, Xvfb, mingw-w64 plus the SDL2 and SDL2_mixer mingw development files), so a fresh checkout needs only Docker:

```bash
native/scripts/test.sh              # gofmt check, go vet, unit tests
native/scripts/build.sh linux       # -> native/dist/openkakutou-linux-amd64
native/scripts/build.sh windows     # -> native/dist/openkakutou-windows-amd64.exe + SDL2.dll + SDL2_mixer.dll (keep them together)
native/scripts/smoke.sh             # runs the Linux build under Xvfb, drives it with real key presses
                                    #   (select -> stage -> setup -> VS -> match), screenshots to native/dist/smoke/
```

Running it: `openkakutou` reads its content from the folder holding the program (on macOS, the folder holding `OpenKakutou.app`, see `ContentRoot` in `native/internal/host`); `-content <dir>` overrides it. The content folder holds `chars/<name>/<name>.def` (one folder per character), `stages/*.def` and `modes/*.jsonc` (the modes; an invalid file is left out with a notice on stderr, and a missing or invalid `versus.jsonc` is replaced by the built-in copy). `internal/game` is the core: it never opens a file, it reads one `fs.FS` rooted at that folder (`os.DirFS` natively, in-memory files elsewhere), and every content path it hands out is a slash-separated name in it. Every content path goes through `ResolvePath`: names match case-insensitively (on-disk spelling returned), `\` is a separator, `..` is resolved textually and may not leave the folder, absolute paths and symbolic links are refused inside the core. An absolute path typed on the command line is mapped by `host.MapPaths` to a name in the folder, or, outside it, to a name under the host file system's reserved `@abs/` directory, so it is used as it is. A stage's `spr` and `bgmusic` are looked up beside its `.def`, then from the content root (Ikemen GO's order, minus `data/`). A character's state files (`st`, `stN`, `cmd`, `stcommon`, `.cns` or `.zss`) are loaded by engine's `LoadFighterProgramFS`, searched in the character folder then in `common/` next to the content root (`CommonFolder`); files found nowhere are logged on stderr, not fatal. A missing `chars/` or `stages/` folder is named on the error screen. The match HUD draws the lifebar named in `config/appearance.json` (`{"lifebar": "<name>"}`), a folder `lifebars/<name>/` holding a MUGEN / Ikemen GO `fight.def`, else `lifebars/default`, else built-in bars; skipped folders and fallbacks are printed on stderr (decision 020, `native/internal/lifebar`). A tiny fixture lives in `native/testdata/content`. Controls default to the web build's (P1 WASD + F/G/H/R/T/Y, P2 arrows + J/K/L/I/O/P, pads A/B/X/Y/LB/RB/Start) and are rebindable in Options > Controls (see `controls.json` below); menus always use arrows/WASD, Enter/Space, Esc/Backspace and a pad's d-pad, A, B and Start, whatever is bound (in a match the pause button is the pad's bound `start`); the game starts on a title screen (Enter or Start), then the main menu lists the installed modes (every file of `modes/`, see [modes.md](modes.md)), Options and Quit, and Enter on a mode starts its flow (Esc goes back, to the main menu from a mode's first screen; quick versus skips all of this); in a match, Esc or the gamepad's bound `start` button opens the pause menu (Backspace and a pad's B are fighter buttons there, not cancel; the pause menu itself closes on Esc, Start, Backspace or B) (Continue, Restart, Character Change, Options, Exit back to the main menu), which freezes the simulation and the sound. Options (main menu and pause menu) opens Gameplay, Audio, Video and Controls screens, rows changed with left/right and saved when the screen is left (Back or Esc) if something changed; audio and video apply at once, gameplay on the next match setup.

Settings live in `config/` of the game folder, one file per concern, each read independently (`native/internal/game/settings.go`, decision 023): `gameplay.json` (`rounds`, odd and at least 1, default 3; `timeLimitSeconds`, 0 or more, default 99; the preselected values of a mode's `matchSetup` screen, a mode without one keeps its own rules), `audio.json` (`master`, `music`, `effects`, each 0 to 100, default 100) and `controls.json` (one section per platform like `video.json`, each `{"p1": {"keyboard": {...}, "gamepad": {...}}, "p2": {...}}`; keyboard actions `up`, `down`, `left`, `right`, `a`, `b`, `c`, `x`, `y`, `z` map to an SDL scancode name (`"W"`, `"Up"`, `"Return"`), gamepad actions `a`, `b`, `c`, `x`, `y`, `z`, `start` to an SDL game controller button name (`"a"`, `"leftshoulder"`, `"start"`; the pad's directions stay on the d-pad and left stick); defaults are P1 `W S A D F G H R T Y`, P2 `Up Down Left Right J K L I O P`, pads `a b x y leftshoulder rightshoulder start`; an action the file lacks keeps its default, an unknown player, device, action, key or button name, or an empty name, makes the whole file invalid; the same name on two actions is kept and shown in red on the screen. Options > Controls > Player 1 or 2 lists each action with its key and button, left/right picks the column, Enter waits for the next key or button (Esc cancels, so Esc itself cannot be bound; any controller button binds while a button is awaited and a pad's B cancels a key wait, so a keyboard Esc is the way out of a button wait), and a key already bound to the other player or another action, or a button already bound to another action of the same pad, is never taken silently: the screen names it (`J is Player 2 A`) and Enter swaps the two bindings while Esc keeps both; Reset to defaults restores both players) and `video.json` (one section per platform, `windows`, `macos`, `linux`, `android`, `web`, each with `fullscreen` default false, `vsync` default true, `windowWidth` and `windowHeight` at least 320 and 240, default 960 and 720; the running platform reads and writes its own section and keeps the others). A missing file means the defaults and is written with them on first launch (creating `config/`); an unreadable or invalid file (including one invalid value) means the defaults for that concern only, a notice on stderr and on the Options screen, and the file is left as it is until the player changes that concern in Options; fields the game does not know are kept when a file is rewritten. A file that cannot be written is a notice, the game keeps running. `-width` and `-height` override the saved window size for that run without saving it. `-frames N -capture out.png` renders N frames, saves a screenshot and exits.

**Audio** (SDL2_mixer): the stage music loops for the whole match and the fighters' sound effects play through up to 16 channels. Tests and the Xvfb smoke run use the dummy audio driver (`SDL_AUDIODRIVER=dummy`, set by `native/scripts/docker.sh`), so they prove the mixer opens, the music loads and the effects reach it, not what is audible. Without a usable audio device the game logs one warning and stays silent. Test audio fixtures: `native/testdata/README.md`. At runtime Linux needs the `libsdl2-mixer-2.0-0` package (plus `libvorbisfile3`/`libmpg123-0` for ogg/mp3 music) and macOS needs `brew install sdl2_mixer`.

**macOS** cannot be built from Linux/Docker. `.github/workflows/native.yml` has a `macos` job (Homebrew SDL2 and SDL2_mixer, `go vet`, `go test` with the dummy audio driver, `go build`) that is **unverified**: it has never been run by the author. Its first real run on GitHub is the first verification, including whether the mixer links and decodes ogg/mp3 there.

**Windows** is cross-compiled in the container and produces a valid PE32+ executable, but it has **not been executed** anywhere: Go binaries do not start under Wine in the container, and no Windows machine was available.

**Dependency note:** `engine` tags are `v2.x` without a `/v2` module path, so Go cannot resolve them by tag; `native/go.mod` pins the tagged commit's pseudo-version instead (see `.vibe/decisions/014`).

**Known gaps in the native build:** stage backgrounds drawn as flat colors (stage sprite layers not rendered), and only character sprites are textured.
